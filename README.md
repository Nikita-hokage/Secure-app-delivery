# Secure App Delivery · RestoreCheck

RestoreCheck проводит репетицию выборочного удаления после восстановления из старой резервной копии. Например, у двух клиентов есть профиль с локальным ID `42`. Один из них запросил удаление. После аварийного восстановления сервис может успешно ответить на `/health`, даже если вернулись его ML-признаки или обработчик стёр профиль другого клиента. RestoreCheck показывает, какая таблица и какая контрольная запись изменились.

## Попробовать за минуту

Нужны Python 3.10+ и SQLite 3.37+ в стандартном модуле Python. Демо создаёт три временных снимка, восстанавливает базу через SQLite Backup API и дважды применяет один журнал удалений. Инструменты командной строки и локальный веб-сервер используют только стандартную библиотеку.

```sh
cd app
python3 -m restorecheck demo
python3 -m restorecheck demo --scenario peer-rewrite
```

Первый запуск выводит `PASS  27/27 checks passed`. Во втором вывод содержит `features/same_tenant: CONTROL_CHANGED  expected=1 actual=1 removed=1 added=1`. У контрольного профиля сохранилась одна строка, но изменилось её содержимое. Команда возвращает код 1.

Для интерактивного стенда запустите из той же папки `python3 app.py` и откройте [127.0.0.1:5000](http://127.0.0.1:5000). Выберите сценарий, затем «Только отклонения». Веб-интерфейс работает на синтетических примерах.

| Сценарий | Что воспроизводит |
| --- | --- |
| `clean` | После восстановления и повторной обработки результат совпадает с ожидаемым. |
| `stale-features` | Профиль и события удалены, в таблице ML-признаков осталась строка. |
| `tenant-collision` | Обработка ID без учёта клиента затронула профиль другого клиента. |
| `peer-rewrite` | Значение признака соседнего профиля изменилось при прежнем количестве строк. |
| `retry-drift` | Первый прогон корректен, повтор затрагивает чужой профиль. |

## Проверить восстановление своего сервиса

1. В тестовой среде выберите три записи с данными в каждой проверяемой таблице. `erase` — удаляемый профиль. У `same_tenant` тот же клиент и другой локальный ID, у `other_tenant` другой клиент и тот же локальный ID.
2. До удаления сделайте консистентный снимок `before.sqlite`. Зафиксируйте запрос на удаление в журнале, который переживает откат базы.
3. В изолированной среде восстановите копию, примените журнал штатным обработчиком сервиса и сохраните `restored.sqlite`. Примените тот же журнал ещё раз и сохраните `retried.sqlite`. Используйте отдельные завершённые SQLite backup-файлы без активных WAL и rollback journal.
4. В JSON-контракте задайте ключи клиентов, профилей и столбцы своих таблиц. Запустите `audit` на этих трёх снимках. Происхождение снимков и фактический запуск обработчика обеспечивает ваш процесс восстановления.

Ниже команда создаёт комплект с известным дефектом в **новой** папке, чтобы попробовать весь путь. Из каталога `app` выполните

```sh
python3 -m restorecheck fixtures /tmp/restorecheck-example --scenario stale-features
python3 -m restorecheck audit \
  --contract /tmp/restorecheck-example/contract.json \
  --before /tmp/restorecheck-example/before.sqlite \
  --restored /tmp/restorecheck-example/restored.sqlite \
  --retried /tmp/restorecheck-example/retried.sqlite --json
```

Минимальный контракт для собственной таблицы

```json
{
  "version": 1,
  "actors": {
    "erase":        {"tenant": "north", "subject": "42"},
    "same_tenant":  {"tenant": "north", "subject": "73"},
    "other_tenant": {"tenant": "south", "subject": "42"}
  },
  "tables": [
    {"table": "profiles", "tenant_column": "tenant", "subject_column": "subject"}
  ]
}
```

Для каждого из трёх профилей в каждой таблице выполняются три сравнения. Первые два сверяют результаты с ожидаемыми данными. Третье сравнивает состояние после первого и второго применения журнала. Проверка учитывает все обычные столбцы, типы значений и кратность одинаковых строк. Порядок строк произволен. JSON-отчёт содержит имена таблиц, роли, этапы и счётчики изменений. Значения строк, ключи клиентов и хеши строк остаются внутри процесса сравнения.

| Код завершения | Значение для CI |
| --- | --- |
| `0` | Все проверки выбранных профилей пройдены. |
| `1` | Есть остаточные данные, потеря или изменение контрольных строк либо расхождение при повторе. |
| `2` | Результат неопределён. Например, отсутствует контрольная строка в исходной копии, изменена схема или недоступен файл. |

**Область проверки.** Версия 1 читает логические строки в объявленных обычных таблицах SQLite. Ключи — текст или 64-битные целые числа. Для базы другой СУБД можно подготовить согласованные SQLite-выгрузки с сохранением типов. Полноту выгрузки обеспечивает экспортёр. Результат относится к выбранным записям. Физические страницы, внешние индексы, объектное хранилище и параметры обученной модели требуют самостоятельных проверок. В демо `features` представляет таблицу производных признаков.

## CI и Kubernetes

Из корня репозитория запустите `python3 -m unittest discover -s tests -v`. Workflow RestoreCheck повторяет тесты и проверяет комплект SQLite-снимков через CLI. Docker запускает тот же WSGI-интерфейс через Gunicorn. Маршрут `/health` используется существующими пробами Kubernetes. Для машинного чтения демо доступны `GET /api/scenarios` и `GET /api/drills/retry-drift`.

## Почему выбрана эта задача

Velero восстанавливает ресурсы Kubernetes и данные томов. AWS Backup позволяет передать результат собственной прикладной проверки после restore job. Fides оркестрирует исполнение запросов на обработку персональных данных. Здесь проверяется результат на уровне приложения. Самое показательное сочетание — совпадающий ID у двух клиентов, проверка содержимого соседних строк и второй прогон одного журнала. Такой тест можно добавить в существующую репетицию восстановления. [Velero](https://velero.io/docs/main/how-velero-works/) · [AWS Backup](https://docs.aws.amazon.com/aws-backup/latest/devguide/restore-testing-validation.html) · [Ethyca Fides](https://github.com/ethyca/fides)

У близких проектов встречаются проверки повторного появления данных после восстановления. Например, команда DataTalksClub описывает сценарии повторной обработки и контрольные записи для собственного сайта. RestoreCheck выносит эту идею в переносимую проверку трёх снимков с контрактом таблиц и двумя контрольными профилями. [DataTalksClub, issue 269](https://github.com/DataTalksClub/website/issues/269)
