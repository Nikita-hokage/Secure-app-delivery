# Secure App Delivery

DevSecOps-стенд для проверки доставки веб-приложения в Kubernetes и сохранности данных после восстановления старой резервной копии. За первую отвечает конвейер GitHub Actions с проверкой доступности и OWASP ZAP. За вторую — **RestoreCheck**, инструмент для сравнения снимков SQLite.

Представьте, что у двух клиентов есть пользователь с локальным ID `42`. Первый клиент удалил свой профиль. После восстановления приложение отвечает на `/health`, но в таблице ML-признаков могли остаться данные удалённого пользователя. Другая возможная ошибка — обработчик удалил профиль `42` у обоих клиентов. RestoreCheck различает эти случаи и показывает затронутую таблицу.

## Попробовать RestoreCheck

Для локального демо нужны Git, Python 3.10+ и SQLite 3.37+ в составе Python. Устанавливать Python-пакеты, Docker или Kubernetes для него не требуется.

```sh
git clone https://github.com/Nikita-hokage/Secure-app-delivery.git
cd Secure-app-delivery
```

Если в вашей копии ещё нет каталога `app/restorecheck`, выполните `git switch feature/restore-rehearsal`. Это ветка с реализацией из [PR № 1](https://github.com/Nikita-hokage/Secure-app-delivery/pull/1).

```sh
cd app
python3 -m restorecheck demo
python3 -m restorecheck demo --scenario peer-rewrite
```

Первый запуск выводит `PASS  27/27 checks passed`. Во втором у соседнего профиля изменилось значение признака. Количество строк осталось прежним, но проверка обнаружила замену.

```text
FAIL  25/27 checks passed
restored       features/same_tenant: CONTROL_CHANGED  expected=1 actual=1 removed=1 added=1
retried        features/same_tenant: CONTROL_CHANGED  expected=1 actual=1 removed=1 added=1
```

Чтобы увидеть расхождение **в браузере**, из каталога `app` запустите `python3 app.py` и откройте [локальный стенд](http://127.0.0.1:5000). Выберите **«Тихая перезапись»** и включите **«Только отклонения»**. Останется одна строка — таблица `features` и соседний профиль. Веб-демо использует синтетические данные.

| Сценарий CLI | Что показывает |
| --- | --- |
| `clean` | Удалённые записи исчезли, контрольные профили сохранились. |
| `stale-features` | Профиль удалён, но его ML-признаки остались. |
| `tenant-collision` | Удаление по локальному ID затронуло другого клиента. |
| `peer-rewrite` | Содержимое соседней записи изменилось при прежнем числе строк. |
| `retry-drift` | Первый запуск корректен, повторное применение журнала удаляет чужие данные. |

## Проверить свои снимки

Восстановите базу в тестовой среде штатным способом. Для команды `audit` подготовьте три отдельных файла SQLite.

| Файл | Когда сделать снимок |
| --- | --- |
| `before.sqlite` | До удаления, когда во всех проверяемых таблицах ещё есть строки каждого из трёх профилей. |
| `restored.sqlite` | После восстановления старой копии и первого применения журнала удалений. |
| `retried.sqlite` | После второго применения того же журнала к восстановленной базе. |

В `contract.json` укажите, чей профиль должен исчезнуть (`erase`), кто остаётся у того же клиента (`same_tenant`) и у кого совпадает локальный ID у другого клиента (`other_tenant`). Имена столбцов задаются отдельно для каждой таблицы.

```json
{
  "version": 1,
  "actors": {
    "erase":        {"tenant": "north", "subject": "42"},
    "same_tenant":  {"tenant": "north", "subject": "73"},
    "other_tenant": {"tenant": "south", "subject": "42"}
  },
  "tables": [
    {"table": "profiles", "tenant_column": "tenant", "subject_column": "subject"}
  ]
}
```

Команды ниже можно попробовать на готовом комплекте. Для проверки своего сервиса укажите в `drill` папку с собственными файлами и выполните только команду `audit`. Рабочий каталог — `app`.

```sh
drill="$(mktemp -d)/drill"
python3 -m restorecheck fixtures "$drill" --scenario stale-features
python3 -m restorecheck audit --contract "$drill/contract.json" \
  --before "$drill/before.sqlite" --restored "$drill/restored.sqlite" \
  --retried "$drill/retried.sqlite" --json
```

`audit` открывает снимки только для чтения. Используйте автономные SQLite-копии, созданные через backup API, без активных журналов WAL или rollback. Проверка охватывает выбранные профили и обычные таблицы из контракта. Она сравнивает все столбцы и учитывает повторяющиеся строки. В JSON-отчёт попадают этап, таблица, роль профиля и счётчики расхождений. Значения строк остаются в процессе проверки.

| Код выхода | Как интерпретировать в CI |
| --- | --- |
| `0` | Все сравнения прошли. |
| `1` | Найдено расхождение. Для примера `stale-features` это ожидаемый результат. |
| `2` | Проверку выполнить не удалось. Проверьте файлы, контракт, схему и наличие исходных записей. |

## Как работает CI

При отправке изменений в `main` GitHub Actions собирает Docker-образ, создаёт временный кластер kind, разворачивает приложение и обращается к `/health`. Затем OWASP ZAP выполняет базовую проверку. Отчёты в HTML, JSON и Markdown доступны в артефакте `owasp-zap-reports` на странице соответствующего запуска. [Конвейер доставки](.github/workflows/security-pipeline.yml) · [История запусков](https://github.com/Nikita-hokage/Secure-app-delivery/actions)

У RestoreCheck есть отдельный workflow для изменений приложения и тестов. Он проверяет CLI на экспортированных снимках и проходит сценарий в Chrome. Для запуска модульных тестов из корня репозитория выполните `python3 -m unittest discover -s tests -v`.
